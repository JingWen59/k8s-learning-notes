# K8s 集群部署踩坑实录

> 在 CentOS 7 + VMware 环境下部署 K8s 1.30 高可用集群（3 Master + 1 Worker）时遇到的真实问题集合。
>
> 每个案例按 **现象 → 排查过程 → 根本原因 → 解决方案 → 经验总结** 结构整理。

## 案例 1：runc 启动容器失败（exit status 127）⭐

### 现象

执行 `kubeadm init` 时，kubelet 日志反复报错：

\```
Failed to create sandbox for pod "kube-apiserver-k8s-master1_kube-system":
rpc error: code = Unknown desc = failed to create containerd task:
failed to create shim task: OCI runtime create failed:
runc did not terminate successfully: exit status 127: unknown
\```

### 排查过程

1. **先看 kubelet 日志**：定位到 runc 报错
2. **手动执行 runc**：
   \```bash
   runc --version
   \```
   报错：
   \```
   runc: symbol lookup error: runc: undefined symbol: seccomp_version
   \```
3. **`exit code 127`** 在 Linux 中通常意味着：
   - 命令找不到
   - 共享库依赖缺失
4. **检查 libseccomp 版本**：
   \```bash
   rpm -qa | grep libseccomp
   # libseccomp-2.3.1-4.el7.x86_64
   \```

### 根本原因

新版 runc 依赖 libseccomp ≥ 2.4，CentOS 7.0 默认的 **libseccomp 2.3.1** 不包含 `seccomp_version` 符号。

### 解决方案

\```bash
yum update -y libseccomp

# 验证
runc --version
# 输出：runc version 1.1.12 ✅
\```

### 经验总结

- **exit code 127** 在容器场景下，几乎都是依赖问题
- 容器运行时的错误要往**底层 glibc / libseccomp** 找
- CentOS 7 默认软件版本过旧，生产环境建议用 **CentOS 7.9** 或 **Rocky Linux 9**
- 排查路线：`容器报错` → `runtime` → `runc` → `系统库`

## 案例 2：containerd 找不到 overlayfs snapshotter ⭐⭐

### 现象

containerd 启动后日志报错：

\```
failed to load plugin io.containerd.grpc.v1.cri
error="failed to create CRI service: failed to find snapshotter \"overlayfs\""
\```

`crictl info` 也报错：

\```
validate CRI v1 runtime API: rpc error: code = Unimplemented
desc = unknown service runtime.v1.RuntimeService
\```

### 排查过程

1. **以为是 overlay 内核模块没加载**：
   \```bash
   lsmod | grep overlay
   # overlay  91659  0   ← 已加载
   modprobe overlay     # 重新加载也没用
   \```
2. **以为是 containerd 配置问题**：重新生成 config.toml 也无效
3. **怀疑文件系统问题**，检查 xfs：
   \```bash
   xfs_info / | grep ftype
   # naming   =version 2  bsize=4096  ascii-ci=0  ftype=0
   \```
   **发现 `ftype=0`**

### 根本原因

`overlayfs` 文件系统要求底层文件系统支持 `d_type`，对应 xfs 的 `ftype=1`。

- CentOS 7.3 之前，xfs 默认 `ftype=0`
- CentOS 7.3 之后，默认 `ftype=1`
- **ftype 在格式化时指定，无法在线修改**

### 解决方案

由于不能重装系统，使用 **loop 设备 + ext4** 替代：

\```bash
# 1. 停 containerd
systemctl stop containerd
rm -rf /var/lib/containerd/*

# 2. 创建 5G 的 ext4 镜像文件
dd if=/dev/zero of=/opt/containerd.img bs=1M count=5120
mkfs.ext4 -F /opt/containerd.img

# 3. 挂载到 containerd 数据目录
mount -o loop /opt/containerd.img /var/lib/containerd

# 4. 开机自动挂载
echo "/opt/containerd.img /var/lib/containerd ext4 loop,defaults 0 0" >> /etc/fstab

# 5. 启动 containerd
systemctl start containerd

# 6. 验证
crictl info | head -5
# RuntimeReady: true ✅
\```

### 经验总结

- 容器运行时对**底层文件系统**有要求
- 装系统前要确认 `ftype=1`（CentOS 7.3+ 默认就是）
- 已有系统可以用 **loop 设备 + ext4** 绕过问题
- 排查思路：`containerd` → `snapshotter` → `overlayfs` → `xfs ftype`

## 案例 3：kubeadm init 卡死在 API Server 启动

### 现象

\```
[api-check] The API server is not healthy after 4m0s
error execution phase wait-control-plane: could not initialize a Kubernetes cluster
context deadline exceeded
\```

### 排查过程

1. **看 kubelet 状态**：active running，没问题
2. **看 kubelet 日志**（被截断的关键信息）：
   \```bash
   journalctl -xeu kubelet --no-pager | tail -50
   \```
   发现 runc 报 exit 127（同案例 1）
3. **修复 libseccomp** 后重试

### 根本原因

底层 runc 启动失败 → 静态 Pod 起不来 → API Server 起不来 → kubeadm 超时。

### 解决方案

参考案例 1，先修 libseccomp，再 reset 后重新 init：

\```bash
# 重置上次失败的状态
kubeadm reset -f
rm -rf /etc/cni /var/lib/etcd $HOME/.kube

# 重启 containerd
systemctl restart containerd

# 重新初始化
kubeadm init --config /root/kubeadm-config.yaml --upload-certs
\```

### 经验总结

- `kubeadm init` 失败的表象往往是 "API Server 启动超时"
- 真正原因要看 **kubelet** 和 **containerd** 的日志
- 排查链路：`kubeadm` → `kubelet` → `containerd` → `runc` → `系统库`

## 案例 4：Calico 镜像 ImagePullBackOff

### 现象

\```bash
kubectl get pods -n kube-system | grep calico
calico-node-xxx  0/1  Init:ImagePullBackOff
\```

`describe pod` 显示：

\```
Failed to pull image "docker.io/calico/cni:v3.28.0":
failed to do request: Head "https://registry-1.docker.io/v2/calico/cni/manifests/v3.28.0":
dial tcp 104.244.43.167:443: connect: connection refused
\```

### 排查过程

1. 直接 `crictl pull docker.io/calico/cni:v3.28.0` → 同样失败
2. 尝试国内镜像：
   \```bash
   crictl pull docker.m.daocloud.io/calico/cni:v3.28.0
   # 报 TLS 证书错误：x509: certificate signed by unknown authority
   \```
3. 系统证书问题：
   \```bash
   yum update -y ca-certificates nss
   \```
4. 再次拉取 → 成功

### 根本原因

- Docker Hub 在国内访问不稳定
- CentOS 7 默认的 ca-certificates 太旧，验证不了新签发的证书

### 解决方案

\```bash
# 1. 更新系统证书
yum update -y ca-certificates nss
update-ca-trust force-enable
update-ca-trust extract

# 2. 用国内镜像源拉取
crictl pull docker.m.daocloud.io/calico/cni:v3.28.0
crictl pull docker.m.daocloud.io/calico/node:v3.28.0
crictl pull docker.m.daocloud.io/calico/kube-controllers:v3.28.0

# 3. tag 成 K8s 期待的名字
ctr -n k8s.io images tag \
  docker.m.daocloud.io/calico/cni:v3.28.0 \
  docker.io/calico/cni:v3.28.0

# 同样处理 node 和 kube-controllers

# 4. 重建 Pod
kubectl delete pods -n kube-system -l k8s-app=calico-node
\```

### 经验总结

- 国内环境部署 K8s **必须配镜像源**
- 常用镜像加速：`docker.m.daocloud.io`、`hub-mirror.c.163.com`
- TLS 证书问题先想到 `ca-certificates`
- 关键命名空间：`ctr -n k8s.io` 才能让 K8s 看到

## 案例 5：PackageKit 占用 yum 锁

### 现象

执行 `yum update` 时一直输出：

\```
Another app is currently holding the yum lock; waiting for it to exit...
The other application is: PackageKit
Memory: 182 M RSS (529 MB VSZ)
\```

等了 10 分钟也不结束。

### 根本原因

PackageKit 是 GUI 系统的包管理后台进程，会**自动检查更新**，导致占用 yum 锁。

### 解决方案

\```bash
# 杀掉进程（PID 替换为实际值）
kill -9 47980

# 永久禁用（如果存在）
systemctl stop PackageKit
systemctl disable PackageKit
\```

### 经验总结

- 服务器版本（minimal）一般没这个问题
- 桌面版 CentOS 安装后建议立即禁用 PackageKit
- yum 锁占用：`/var/run/yum.pid`

## 案例 6：kube-controller-manager 反复崩溃（CrashLoopBackOff）

### 现象

集群正常运行后发现：

\```
kube-controller-manager-k8s-master1   0/1   CrashLoopBackOff   11
kube-controller-manager-k8s-master2   0/1   CrashLoopBackOff   9
kube-controller-manager-k8s-master3   0/1   CrashLoopBackOff   8
\```

3 台 Master 都崩溃。

### 排查过程

\```bash
kubectl logs -n kube-system kube-controller-manager-k8s-master1 --tail=50
\```

关键日志：

\```
E0510 leaderelection.go:340] Failed to update lock optimistically:
context deadline exceeded, falling back to slow path

E0510 leaderelection.go:347] error retrieving resource lock
context deadline exceeded

I0510 leaderelection.go:285] failed to renew lease
kube-system/kube-controller-manager: timed out waiting for the condition

E0510 controllermanager.go:304] "leaderelection lost"
\```

### 根本原因

- Master 节点资源不足（2核2G）
- etcd 响应慢，超过 leader election 的 renewal deadline
- 失去 leader
